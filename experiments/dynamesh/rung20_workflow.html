rung20, Line by Line

Every operation the training script performs, in execution order, with the tensor shapes and constants it actually uses. Written from the source, not from memory — each claim below carries the line it comes from. The one question this document exists to settle: where gradients reach, and how an edit admitted at cross-attention arrives at geometry the camera never saw.

The single sentence

A rank-4 LoRA on cross_attn.to_kv in all 30 blocks of the frozen texture-flow transformer is trained to make the render of a fixed mesh under a fixed camera and fixed noise match 150 per-frame targets, so that the only thing distinguishing one frame from another is the image conditioning — and therefore the only thing the adapter can learn is a function of that conditioning.

Rung number is computed, not named — L335–340

The filename does not decide the rung. A cascade over the flags does, and it is evaluated at runtime:

_RUNG = (24 if (conf_ramp_qlo >= 0 and conf_ramp_qhi >= 0)
    else 22 if (lambda_con > 0 and lambda_smo <= 0)
    else 21 if (lambda_con > 0 or lambda_smo > 0)
    else 20 if conf_weight
    else 23 if lambda_smooth > 0
    else {'kv': 17, 'kvo': 18, 'v': 19}.get(targets, 17))

rung20 is exactly: --conf-weight on, every regulariser off. Turn the trust map off with the same target set and the identical file produces rung17.

Run id — L296–344

A _CFG dict is hashed with md5 and truncated to 8 characters. The directory is runs/rung20_{blocks}_{targets}_r{rank}_s{seed}_{RUN_ID}, and stdout is tee'd into train.log inside it.

Two omissions from this hash cost real runs

mesh, gt_dir, gt_render_dir were absent until 2026-08-11. spot_star and spot_lava differ only in those paths, so they hashed identically, landed in one directory, and the second job resumed from the first's lora_e001.pt — 29 epochs of cow-spot weights trained on lava data, detectable only as 59 rows in a 30-epoch CSV.

render_res had the same gap: the teapot at 518 and at 960 would have collided. Both are now in the hash and in the resume guard (L1765), which refuses to resume a checkpoint whose mesh, targets or render resolution differ.

Frame split — L280–294

HELD_OUT   = []          # --held-every defaults to 0
TRAIN      = [1 .. 150]
ALL_FRAMES = [1 .. 150]
MONITOR    = ALL_FRAMES[4::10]   # 5, 15, 25 ... 145 — 15 frames

There is no held-out set. The code says why: the task is "this mesh, these 150 textures from this video," so every frame is part of the deliverable. Reported numbers come from evaluate(ALL_FRAMES), and the checkpoint is selected on MONITOR, a subset of the same frames. Every PSNR in this project is training-frame reconstruction. Defensible for a per-object fit; it must be stated as such.

01

The adapter

What is created, where it attaches, and what it costs.

LoRALayer — L368–389

A = Parameter(empty(rank, in_dim));  kaiming_uniform_(A, a=sqrt(5))
B = Parameter(zeros(out_dim, rank))
scaling = alpha / rank

forward(x) -> ((x.float() @ A.T) @ B.T) * scaling

B is zero-initialised, so at step 0 the delta is exactly zero and the model reproduces frozen TRELLIS.2 bit for bit. GATE-plain asserts this. With α=4 and r=4 the scaling is exactly 1.0, which reproduces every run made before the α/r factor was introduced.

Which projection, and why that one — L402–414, L266–272

ModuleShapeInput isrung20
cross_attn.to_q1536 → 1536the 3D tokensfrozen
cross_attn.to_kv1024 → 3072the image tokensLoRA
cross_attn.to_out1536 → 1536the attention outputfrozen
self_attn.*—the 3D tokensfrozen
mlp, adaLN_modulation——frozen

Input widths settle the argument. to_q takes 1536 — the 3D token width. to_kv takes 1024, the DINOv3 token width. It is the only weight matrix in the network whose input is the image.

params = rank × (1024 + 3072) × 30 blocks
       = 4 × 4096 × 30
       = 491,520          # 0.038% of the 1.29B texture DiT

How it attaches — L440–470

Not by replacing modules — by forward hooks installed inside a context manager, so the base model is never mutated:

def _kv(mod, inp, out, _lb=lb):
    return out + _lb.to_kv(inp[0]).to(out.dtype)

blk.cross_attn.to_kv.register_forward_hook(_kv)

Blocks outside the active set receive no hook at all and run exactly frozen — which is what makes --blocks early/mid/late a clean placement comparison rather than a weighted one.

02

Setup — everything computed once

The mesh, camera, conditioning, targets, noise and trust map are all constants. Per-step work is only what the gradient needs.

The two coordinate frames — L600–609

v_raw

The mesh as exported, already registered. Used for rasterisation, so the image lines up with the video. Normals and the eye vector live here too.

v_pp

The same vertices after preprocess_mesh — normalised to [−0.5, 0.5], axes permuted. The PBR voxel field lives in this frame, so v_pp is what gets interpolated to give each pixel its sampling position.

preprocess_mesh preserves faces and vertex order, so v_raw[i] and v_pp[i] are the same vertex. That correspondence is what lets both frames coexist.

SurfaceRenderer — rasterise once — L612–671

full_proj = intrinsics_to_projection(intr, NEAR, FAR) @ ext
rast      = dr.rasterize(ctx, v_clip, faces, (res, res))
mask      = rast[0,...,3] > 0                 # the silhouette, constant
mask_idx  = nonzero(mask.reshape(-1))

eye     = -(R.T @ t)                          # = (0, -2, 0)
cos_inc = |normalize(n) · normalize(p - eye)|   # per-pixel incidence

pos     = interpolate(v_pp, rast)[mask_idx]  # [K,3] sampling points

dx, dy    = screen-space derivatives of pos
footprint = ||cross(dx, dy)||                 # surface area one pixel covers
fp_valid  = both neighbours inside the mask   # no silhouette-straddling diffs

Mesh and camera never move, so the raster, the silhouette, each pixel's 3D surface point, its incidence and its footprint are all computed once and reused for all 150 frames × 30 epochs.

Conditioning — L1133–1186

Reproduced deterministically rather than by calling preprocess_image(), and the reason is stated in the source: that function runs BiRefNet per frame and crops to that frame's own bbox, so both the matte and the framing would jitter frame to frame — and that jitter would be indistinguishable from texture change.

alpha  = largest_component(min(RGB) < 245)     # per frame
bbox   = square box around the UNION of all 150 alphas
crop, then premultiply by alpha                # background becomes BLACK
cond   = pipe.get_cond([img], resolution).detach()

shape  (1, 1029, 1024)   # DINOv3 tokens, cached once, frozen

The union crop means identical framing for every frame, contributing exactly zero to any temporal measurement. Handing the raw 960² frame instead — a small object in a large white field — is far out of distribution and yields a black texture.

Targets — L1166–1182

gts[fi]      = gt_{fi}.png       -> [1,H,W,3] in [0,1]
gt_masks[fi] = valid_{fi}.npy    # which target pixels are real

An earlier version loaded valid_ and then overwrote it with the raw video's silhouette, which knows nothing about which target pixels were fabricated. That let 447 pure-white pixels per frame into the loss for all 30 epochs, and the adapter learned to paint them white. The comment at L1180 reads: "Do not add a second assignment here."

Shape latent and noise — L1121–1196

shape_slat = pipe.encode_shape_slat(mesh_pp, resolution)   # ENCODE, not sample
ss_n       = (shape_slat - ss_mean) / ss_std

g          = Generator(cpu).manual_seed(42)
noise      = ss_n.replace(feats=randn(n_vox, flow.in_channels - ss_n.feats.shape[1]))

This is the experimental control. shape_slat is a deterministic encode of a fixed mesh. The noise is drawn once and reused for every frame. So across the 150 frames the only input that varies is the image conditioning — and any change the adapter learns is therefore attributable to the cross-attention pathway and nothing else.

The trust map — L1475–1553

w = cos_inc / footprint.clamp_min(1e-12)
w = where(fp_valid, w, 0)
w = w * (cos_inc >= TAU)          # TAU = 0.25, a hard step in rung20
w = where(mask, w, 0)
w = w / median(w[w > 0])           # normalise so the median weight is 1.0

assert kept / covered > 0.4

Measured, teapot at 518²: 28,559 covered, 27,088 kept (94.8%), 1,471 discarded — all in a thin band at the rim. At 960² the same τ keeps 95.1%.

Both factors matter and they are not redundant: incidence alone misses high curvature at the silhouette, which inflates the footprint even where the cosine is not yet small. (L654–660)

GATE-resume is the fix for the spot_star / spot_lava collision described in stage 00.

04

One training step

Executed 150 × 30 = 4,500 times. This is the whole of it.

for ep in 1..30:
  order = rng.permutation(TRAIN)               # reshuffled every epoch
  for fi in order:

    k   = rng.integers(0, 12)                 # a knot of the REAL schedule
    t_k = T_SEQ[k]

    with lora_ctx(flow, reg):                  # hooks installed

        x_k = run_ode(flow, noise, conds[fi], ss_n, T_PAIRS[:k])
                                                 # k Euler steps, no_grad, LoRA ACTIVE
        v   = flow_eval(flow, x_k, t_k, conds[fi], ss_n)
                                                 # ONE evaluation, WITH grad
        x0  = pred_to_xstart(x_k, t_k, v)        # the sampler's own helper

        img = decode_render(x0, clamp=False)
        _m  = renderer.mask & gt_masks[fi]

        _se = ((img - gts[fi])**2)[0][_m]        # [N,3]
        _wm = conf_w[_m]                         # [N]
        loss = (_wm[:,None] * _se).sum() / (_wm.sum()*3).clamp_min(1e-9)

        opt.zero_grad(set_to_none=True)
        (loss * 4096).backward()                 # INSIDE the context

    for p in reg.parameters(): p.grad.div_(4096)
    clip_grad_norm_(reg.parameters(), 1.0)
    opt.step()                                   # AdamW, lr 1e-4, wd 0

Seven details that are load-bearing

k is drawn from the real schedule

STEPS=12, RESCALE_T=3.0 gives T_SEQ = 3t/(1+2t), which is front-loaded — seven of twelve knots sit above t=0.75. Drawing k from this list rather than uniform [0,1] means the adapter is never trained where inference never goes. L751–759

Backward must be inside lora_ctx

Gradient checkpointing recomputes the flow forward during backward. With .backward() outside the block the recomputed graph is the bare model and torch raises CheckpointError: forward 74 / recomputation 57 — the 17 missing tensors being exactly the LoRA deltas. L1812–1820

clamp=False during training

torch.clamp has exactly zero gradient outside its range, so a voxel pushed past 1.0 is frozen there forever — the loss still reports it as too bright, but no gradient can bring it back. A one-way ratchet into white. Metrics and saved images still clamp. L677–683

LOSS_SCALE is mandatory

The decoder is fp16 and its gradients underflow. Measured: scale 1 → sum|grad| 0.0000e+00, scale 4096 → 4.6620e+03. Divided back out of reg.grad before the optimiser step, so the effective lr is unchanged. L1332–1340

The prefix runs with the adapter active

run_ode is called inside lora_ctx, under no_grad. This matches inference, which also has the adapter active for all 12 steps. The prefix contributes no gradient but does place xk on the adapted trajectory. L893–899

The loss region is the intersection

renderer.mask & gt_masks[fi]. Because make_gt_targets.py fills 100% of our silhouette, valid_ is all-true, so the region equals our silhouette and is constant across frames — which GATE-region asserts, and which is what makes PSNR comparable between frames and between arms. L1260–1276

Only the adapter is optimised

AdamW(reg.parameters()). The decoder's weights carry requires_grad only to stop flex_gemm returning grad_weight=None; nothing optimises them and their .grad is cleared each step so it cannot accumulate. L1757, L1874

Why one graded step and not twelve

Backpropagating through all 12 ODE steps means 12 sequential 1.3B forward passes with activations retained. Instead k is resampled every step, so over an epoch the adapter still sees every timestep — just one at a time. x0 uses FlowEulerSampler._pred_to_xstart directly rather than a reimplementation, so the rectified-flow parameterisation cannot drift from TRELLIS.2's.

05

Where the gradient actually reaches

The propagation question, answered from the code rather than by analogy.

The backward path, narrowest point first

renderer.sample() grid-samples the PBR field at self.pos
    → pos = interpolate(v_pp, rast)[mask_idx]
    → i.e. ONLY the surface points visible to the training camera

so d(loss)/d(voxel feature) is non-zero only for voxels
trilinearly touched by those visible points.

Measured for this mesh and camera: the training view resolves 18.4% of vertices with a target in every frame (39,708 of 215,462). The rest of the object contributes nothing to the loss.

But the parameter is shared, and that is the mechanism

to_kv does not transform voxels. It transforms the 1029 image tokens, once per block, producing the keys and values that every voxel then attends to. So:

  • the gradient arrives only from the ~18% of voxels the camera resolves;
  • the learned delta is applied to the K,V that all voxels read, in all 30 blocks;
  • therefore voxels on the back do receive the adapted conditioning — they are unsupervised in the loss, not absent from the forward pass;
  • and self_attn, left frozen, mixes across voxels downstream of every one of those 30 cross-attention reads.

This is the bet the file's own docstring states at L15–20: "an edit admitted at cross-attention gets distributed by TRELLIS's own machinery to voxels the camera never saw. That bet is what this experiment tests, and the turntable decides it — not PSNR from the training view."

What the mechanism can and cannot supply

The conditioning is one image of one viewpoint — get_cond([cond_img], ...), a single view, 1029 tokens. A voxel on the back cross-attends to that same token set. The adapter changes what those tokens say; it cannot add information about a surface the video never showed.

Measured on teapot_lava2, interior pixels only, mean gradient magnitude:

Regionedge detailcontrast (std)
GT target9.8242.50

Two separable losses. The front gap (5.44 vs 9.82) occurs where every pixel is supervised, so it is not a propagation limit — masked MSE is minimised by the local mean, and --w-lpips is inert in this environment (no lpips package; L262–264). The back gap is the propagation limit: material and its temporal evolution transfer, high-frequency pattern does not.

The claim that survives review: the adapter carries the material and its evolution to unsupervised geometry. The claim that does not: that it reproduces the pattern there. The turntables show this plainly and a reviewer will see it in one glance.

What the literature says about these choices

Read against ~40 papers on 3D texture generation and adapter design. Three verdicts: validated, unprecedented, behind the field.

validated  The adapter design

Choice herePrecedentWhat they found
train only cross-attn K/V, backbone frozenIP-Adapter
arXiv 2308.06721		 “only the parameters of the new cross-attention layers are trained, while the original UNet remains frozen” — K,V from the reference image, Q from the noisy tokens. 22M params matches full fine-tuning. This is our structure exactly.

arXiv 2307.04725		 motion module on a frozen T2I; “spatial attention layers are never modified.” Same separation of concerns, along time instead of space.
K and V are different pathwaysPerfusion
arXiv 2305.01644		 K is a “where” pathway setting the attention map; V is a “what” pathway setting appearance. Training K makes attention “spread across the entire image rather than focusing on the object.”

arXiv 2407.02430		 “textures over areas not facing the camera are less reliable”; blended “by a weighted average by incidence angles, using cosine similarity between the viewing direction and per-pixel normal.” Our trust map is standard practice.
One place our measurement contradicts the literature

Perfusion’s prescription is to lock K and adapt V alone. We implemented that (--targets v, rung19) and it scored 21.41 against to_kv’s 22.30 on the teapot — the recommended variant was worse. Cite Perfusion for the K/V distinction, not as endorsement of a configuration our own ablation beat.

unprecedented  Single-camera supervision

Six families exist in the texture-generation literature, and every one of them exists to avoid supervising from a single fixed view:

FamilyRepresentativeHow it reaches unseen surface
iterative view-by-view inpaintingTEXTure, Text2Tex, InTeXrotate and inpaint newly visible texels, guided by a generation mask — makes the unseen seen
synchronised multi-view diffusionSyncMVD, TexFusion, MVPaint, SyncTweediesdenoise in N cameras at once, aggregate through a shared UV/latent map after every step so views reach consensus early
UV-space diffusionPaint3D, GenesisTexwork in texture space, so unseen regions are simply holes to inpaint
learned backprojectionIm2SurfTexreplaces ad-hoc cosine averaging with a trained attention module over 3D position, normal and geodesic distance
attention-level propagationEpiDiff, StyleAligned, GenesisTex2epipolar or shared K/V attention between views, often inserted into a frozen model
explicit back-view hallucinationSiTH, CaPagenerate the missing view with a diffusion prior, then reconstruct from front + back

We are in none of them. One fixed camera, and the unseen surface is reached only by the frozen self-attention propagating a cross-attention edit. That is genuinely novel — and it is also the direct explanation for the measured 2.62 vs 9.82 sharpness gap on the far side. The field’s consensus is that pattern cannot be placed on a surface no camera observed; our numbers are that consensus appearing in our own data.

Consequence for the write-up: the defensible claim is that material and its temporal evolution transfer to unsupervised geometry. Not that the pattern does.

behind the field  The loss

Masked MSE alone, with --w-lpips inert. The failure mode has a name and a literature:

  • Rethinking SDS arXiv 2505.01888 — score distillation “is mean-seeking and tends to create an average of plausible generation results,” producing “overly smoothed texture.” Masked MSE has the identical pathology: its minimiser at an uncertain pixel is the local mean.
  • GenesisTex2 arXiv 2409.18401 — names “blurring, over-saturation, or over-smoothing” as the recurring failure of the whole field.
  • Tex4D arXiv 2410.10821 — hit exactly this: “combining video diffusion models and UV texture aggregation initially led to blurry results.” Their fix was a modified DDIM sampling process plus a reference latent texture strengthening frame-to-frame correlation.
  • Perceptual loss is the standard remedy — documented to reduce blurriness and structural inconsistency.

This is the one defect inside this file that the literature predicts will produce the blur we measure at the front, where every pixel is supervised and propagation cannot be blamed.

A hypothesis that was tested and rejected

58% of training steps land at t ≥ 0.75, where x0_hat is closest to a conditional mean, which suggested the timestep schedule might be driving the smoothing. Measured and false: mean MSE across the twelve knots is flat (0.011–0.025, no trend with t). The schedule is not the cause.

caution  Two claims to withdraw

ClaimWhy it does not hold
“rank 4 is optimal” rsLoRA arXiv 2312.03732 shows α/r scaling makes “the effective gradient magnitude and output activations of the adapter collapse as r increases.” Our sweep ran under α/r, so a flat curve across r ∈ {1…32} measures the scaling, not the rank. Say “the smallest rank that works,” not “optimal.”
the rung21/22 regularisers were the right shape RegNeRF arXiv 2112.00724 is the principled version: sample unobserved viewpoints and regularise the rendered patches against a learned image prior, rather than penalising voxel features directly. If unsupervised-region regularisation is revisited, that is the formulation.
Nearest prior work — must be cited

Tex4D is “the first method specifically designed for 4D scene texturing,” producing multi-view and temporally consistent textures for mesh sequences, zero-shot. The differentiators are real — it needs a mesh sequence and a text prompt, we take one fixed mesh and a real video and train an adapter — but a reviewer who knows Tex4D and does not see it cited will assume we do not.
